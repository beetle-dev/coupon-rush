# Coupon Rush

한정 수량 쿠폰 발급에서 **5가지 동시성 제어 방식의 정합성과 처리 성능을 비교·분석한 개인 프로젝트**입니다.

📑 **프로젝트 소개 자료:** [PPT에서 상세 내용 보기](https://drive.google.com/file/d/1G92nUKtw93xzWWpdLruYTcAPcNTHGRop/view?usp=sharing)

## 1. 프로젝트 배경

실무에서 사전 생성한 쿠폰을 DB에 저장한 뒤 요청 시 할당하는 시스템을 구현하면서, 요청이 집중될 때 초과 발급과 처리 지연을 어떻게 방지할지 고민하게 되었습니다.

이를 검증하기 위해 **재고 1,000개에 발급 요청 10,000건이 몰리는 상황**을 구성했습니다. 동시성 제어가 없는 구현을 기준으로 비관적 락부터 Kafka 비동기 영속화까지 단계적으로 적용하며, 정합성을 확보하고 처리 지연을 줄이는 과정을 비교했습니다.

| 구분 | 기술 |
|---|---|
| 애플리케이션 · DB | Java 17 · Spring Boot 4.1 · JPA · MySQL 8 |
| 동시성 · 비동기 처리 | Redis · Redisson · Lua · Apache Kafka |
| 테스트 · 검증 | JUnit 5 · Testcontainers · k6 |

## 2. 검증 방식

동일 이벤트의 **잔여 재고**를 경합 대상으로 두고, 초기 수량을 초과하지 않으면서 사용자당 이벤트별 1매만 발급되는지 확인했습니다.

| 구분 | 시나리오 | 확인 항목 |
|---|---|---|
| JUnit 동시성 테스트 | 재고 1,000개 · 32개 스레드 · 요청 10,000건 | 초과 발급 여부 · 동일 사용자 중복 발급 여부 |
| k6 부하 테스트 | 재고 1,000개 · 5초 동안 최대 3,000 VU로 증가 · 요청 10,000건 | TPS · p95 응답 시간 · 예상외 응답 비율 · 요청 완료율 |
| 비동기 저장 검증 | 발급 접수 이후 DB 반영 결과 확인 | 접수 건수와 DB 반영 건수의 일치 여부 |

## 3. 단계별 결과

| 단계 | 방식 | TPS (건/초) | p95 응답 시간 | 초과 발급 |
|---|---|---:|---:|---:|
| 0 | 동시성 제어 없음 | 217.1 | 13.76초 | 9,000건 |
| 1 | 비관적 락 | 381.0 | 11.71초 | 0건 |
| 2 | 낙관적 락 + 재시도 | 161.4 | 36.99초 | 0건 |
| 3 | Redis 분산 락 | 167.5 | 17.82초 | 0건 |
| 4 | Redis Lua + 동기 DB 저장 | 1,346.3 | 2.71초 | 0건 |
| **5** | **Redis Lua + Kafka 비동기 영속화** | **2,240.1** | **0.74초** | **0건** |

최종 단계에서는 **1,000건을 접수하고 초과 발급 0건**을 기록했습니다. 응답 종료 직후 접수 건수와 DB 반영 건수의 차이도 0건이었습니다. Redis Lua 동기 저장 단계 대비 처리량은 **약 1.66배** 증가했습니다.

## 4. 성능 개선 과정

1. **락으로 초과 발급 방지** — 비관적 락, 낙관적 락과 재시도, Redis 분산 락 모두 실험에서 초과 발급을 막았습니다. 다만 동일 재고에 요청이 집중되면서 잠금 대기나 충돌·재시도에 따른 성능 한계가 나타났습니다.
2. **Redis Lua로 DB 유입량 감소** — 발급 기간·중복·재고 검사와 재고 선점을 원자적으로 처리했습니다. 발급 불가 요청 9,000건을 DB 접근 전에 종료하며 처리량과 응답 시간이 개선되었습니다.
3. **Kafka로 DB 저장을 요청 경로에서 분리** — 재고 선점 후 Kafka ACK를 확인하고 접수 응답을 반환하며, Consumer가 DB 저장을 수행하도록 변경했습니다. 성공 요청도 DB 커밋을 기다리지 않게 되었습니다.

핵심은 **경합 범위와 DB에 도달하는 요청 수를 줄이고, 응답 전에 기다리는 작업을 줄이는 것**이었습니다.

## 5. 회고 및 개선 과제

**회고**

- 같은 재고에 요청이 집중되는 조건에서는 낙관적 락의 재시도 비용이 컸습니다. 기술 선택에 앞서 경합의 집중도와 범위를 파악해야 했습니다.
- 비동기화 이후에는 응답 속도뿐 아니라 접수된 요청의 최종 DB 반영까지 검증해야 했습니다.
- 동기 저장 완료가 필요한지, 접수 후 처리를 허용할 수 있는지에 따라 적합한 구조가 달라졌습니다.

**개선 과제**

- **발급 상태 관리:** 대기·완료·실패 상태를 조회하고 최종 실패 알림을 받을 수 있도록 개선할 계획입니다.
- **부분 실패 복구:** Redis 선점 후 Kafka 발행 전 프로세스 종료, 재고 보상 실패 등을 검증하고 미완료 요청의 재처리·재고 복원 절차를 마련할 계획입니다.
- **병목 관측:** DB 잠금·커넥션 대기와 Kafka 소비 지연을 함께 측정해 지연 원인을 확인할 계획입니다.
