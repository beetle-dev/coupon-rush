## 1. 프로젝트 개요

실무에서 사전 생성된 쿠폰을 DB에 저장한 뒤 요청 시 할당하는 시스템을 구현하면서, **트래픽이 증가해도 초과·중복 발급 없이 빠르게 처리하려면 어떤 동시성 제어 방식이 적합할지** 고민하게 되었습니다. 이를 검증하기 위해 재고 1,000개에 요청 10,000건이 몰리는 상황을 가정하고, 방식별 정합성과 처리 성능을 비교했습니다.

락 없는 구현을 기준으로 5가지 제어 방식을 단계적으로 적용했습니다. 구현 범위는 이벤트 등록·조회, 쿠폰 발급·조회, 1인 1매 제한, 재고·발급 기간 검증입니다.

| 구분 | 구성 |
|---|---|
| 기술 스택 | Java 17 · Spring Boot 4.1.1 · JPA · MySQL 8 |
| 동시성·메시징 | Redis 7 · Redisson · Lua · Kafka 4 |
| 검증 도구 | JUnit · Testcontainers · k6 · Docker |
| 테스트 환경 | Ryzen 7 4800H · RAM 16GB · Windows 10, 로컬 PC 1대 |
| 부하 실험 설정 | Tomcat 최대 스레드 400 · HikariCP 최대 연결 50 · 연결 대기 10초 |

## 2. 검증 방식 및 성공 기준

- **정합성 검증:** JUnit에서 32개 스레드로 10,000건을 요청하고 발급 수와 잔여 재고를 확인했습니다. 동일 사용자의 반복 요청과 메시지 중복 처리도 별도로 검증했습니다.
- **성능 측정:** k6로 5초 동안 최대 3,000 VU까지 부하를 높여 서로 다른 사용자 10,000명의 요청을 전송하고, TPS와 p95 응답 시간을 비교했습니다.

| 검증 항목 | 검증 도구 | 확인 방법 및 성공 기준 |
|---|---|---|
| 초과 발급 | JUnit + k6 | [실제 DB 쿠폰 수 기준 초과 0건](src/test/java/com/couponrush/coupon/service/CouponConcurrencyIssueAsyncTest.java#L57) · [성공·접수 응답 수 기준 초과 0건](k6/coupon-issue.js#L141) |
| 중복 발급 | JUnit | [동일 사용자의 동시 요청에도 한 장만 접수·저장](src/test/java/com/couponrush/coupon/service/CouponConcurrencyIssueAsyncTest.java#L113) |
| 요청 처리 | k6 | [요청 완료율 100%](k6/coupon-issue.js#L142) · [예상외 응답률 0%](k6/coupon-issue.js#L54) |
| 비동기 저장 | JUnit + k6 | [접수 수와 실제 DB 저장 건수 일치](src/test/java/com/couponrush/coupon/service/CouponConcurrencyIssueAsyncTest.java#L57) · [접수 수와 DB 잔여 재고로 계산한 반영 건수 일치](k6/coupon-issue.js#L146) · [메시지 재전달 시 중복 저장 없음](src/test/java/com/couponrush/coupon/message/CouponIssueMessageConsumerTest.java#L43) |

TPS는 성공·접수·거절을 포함한 초당 처리 요청 수이며, 품절·중복 등의 `409`는 예상된 응답으로 분류합니다. 비동기 단계는 `202` 접수 이후 DB 반영도 확인합니다.

> **최종 단계 결과:** Baseline 대비 요청 처리량 **약 10.3배**, p95 응답 시간 **약 94.6% 단축**. 재고 1,000개에 **1,000건 접수**, 초과 발급 **0건**을 기록했습니다.

- 동기 단계는 DB 저장 완료까지, 최종 비동기 단계는 **접수 완료까지의 응답 시간**을 측정했습니다.
- 최종 비동기 단계에서는 접수 1,000건과 DB 반영 건수도 일치했습니다.

## 4. 각 단계의 특징 및 한계

| 방식 | 핵심 특징 | 한계 |
|---|---|---|
| 락 없음 | 조회한 재고를 차감하고 쿠폰 저장 | 여러 요청이 같은 재고를 읽고 발급을 진행해 **초기 수량보다 많은 쿠폰이 발급될 수 있음** |
| 비관적 락 | DB 행을 잠가 재고 검사·차감을 순차 처리 | 같은 이벤트의 요청을 한 건씩 처리하므로, 요청이 몰리면 **잠금 대기가 길어져 응답이 느려짐** |
| 낙관적 락 | 버전 충돌을 감지하고 재시도 | 같은 재고를 동시에 변경하려는 요청이 많으면 실패한 작업을 반복하게 되어 **처리량이 줄고 응답 시간이 길어짐** |
| Redis 분산 락 | Redis에서 이벤트별 락을 획득한 뒤 발급 | 락을 Redis에서 관리해도 DB 저장까지 한 건씩 처리하므로, **DB 저장이 느려지면 뒤의 요청도 함께 지연됨** |
| Redis Lua | 검사와 재고 선점을 원자적으로 처리해 품절·중복 요청을 DB 앞에서 차단 | 품절·중복 요청은 빠르게 차단하지만, **발급 가능한 요청은 여전히 DB 저장을 기다려야 함**. 저장에 실패하면 Redis 재고만 줄어든 상태가 남을 수 있음 |
| Redis Lua + Kafka | 재고 선점 후 메시지를 전달하고 DB 저장을 Consumer로 분리 | **접수 응답을 받아도 실제 발급이 완료된 것은 아님**. 이후 메시지 전달·DB 저장에 실패하면 쿠폰이 저장되지 않을 수 있어, 최종 결과 확인과 복구가 필요함 |

## 5. 회고 및 개선

**회고**

- 정합성을 확보한 방식 사이에서도 성능 차이가 컸습니다. 처리량과 응답 시간을 함께 비교해야 기술 선택의 근거를 얻을 수 있었습니다.
- 락의 위치를 바꾸는 것보다 **불필요한 DB 접근과 응답 전 대기를 줄이는 방향**이 효과적이었습니다.
- 비동기화는 응답을 빠르게 했지만 복구와 상태 관리가 복잡해졌습니다. 성능뿐 아니라 **구현 복잡도와 동기 완료 요구사항**도 함께 고려해야 했습니다.

**개선 과제**

- 비동기 발급의 대기·완료·실패 상태 조회와 실패 알림
- 장애 상황에서 Redis 재고와 DB 발급 이력의 불일치 검증·복구
- DB 잠금·커넥션 대기, Kafka 메시지 처리 지연 관측으로 병목 원인 확인
